# Winnow E4B image parity

Measured on 2026-10-02, Arch Linux, RTX 4070 12GB and x86-64 CPU. The test uses the unmodified
llama.cpp b11146/v0.5.0 libraries and stock llama-server at
`7fe450e19305b828c199d602c23a8337aaa1f03b`, staged from the official archive by `scripts/llama-cpp.sh`.

## Pins and results

- Language model: `EldanRing/Winnow-E4B@734302fe5fbfeb3f21a7ece62653c9539be4aaf3`,
  `gguf/Winnow-E4B-Q8_0.gguf`, SHA256
  `840e3f50e5a9c218727f44e121d1b37cc9e2c3b318c8eb422ba6ef2e27b618a2`.
- Projector: same revision, `gguf/mmproj-Winnow-E4B.gguf`, SHA256
  `ddf46c21d7078e95338cfc22306b19b276a29a5ad089023449dd54d4b6170a51`.
- Image parity context: 2,048; batch 2,048; microbatch 512; one sequence; full SWA.
- CUDA: 21 requests, 65/65 decisions; maximum normalized option-logit error `9.5502737e-6`.
- CPU: 21 requests, 65/65 decisions; maximum normalized option-logit error `1.1467874e-5`.
- The unchanged tolerance is `1e-3`, as in `parity_llama`. Each device uses its own stock reference.
- Coverage: choice/noul/score, ordered criteria, multiple questions, two-image order reversal,
  changed/repeated images, objects/arrays/Unicode/escaped control tokens in state, RGB patterns
  and different image sizes. Input position accounting also matches the reference.
- Native HTTP (both the 2,048-token test profile and shipped 8,192-token manifest): valid PNG and data URL, 2 and 16 images (including encoder batch rollover), invalid base64/PNG, 17-image rejection,
  context overflow, successful request after rejection, text compatibility, and explicit unload.
- Full text regression: 123 requests (15 rejected), 505/505 decisions, maximum normalized option-logit
  error `1.138e-5`, maximum calibrated probability error `2.303e-6`.

The text source is [the maintainer's fixture](https://gist.github.com/cobanov/c808f61976a8210235d8faf8ae91aa15),
SHA256 `b0b15b5646e8cda17364b6097a9613eb231a88a4813b52c129423313447695fe`.
Direct comparison to its RTX 4090 numbers gives 502/505 decisions and max logit error `0.2822` on
this RTX 4070. Replaying the unchanged prompts through stock llama-server on the RTX 4070, using
the repo's existing `llm_common.replay`, gives the passing result above. The tolerance is unchanged;
this follows ADR 0003's same-device reference, not a cross-device numerical-equivalence claim.

## Reproduce image parity

Fetch the pinned author files and stage libraries with `scripts/llama-cpp.sh`. Use the stock
`llama-server` executable from that same archive. Save `decision.json` and `calibration.json` from
the E4B export pipeline. For the measured 2,048-token profile, change only `llama.n_ctx` in the
local test copy of `decision.json`. Leave the registry's 8,192-token configuration unchanged.

Run the reference first, then stop it before loading the Rust runner, so two language models do
not compete for GPU memory. Substitute absolute paths for MODEL, PROJECTOR, and LIBRARY_DIR:

```sh
llama-server -m MODEL --mmproj PROJECTOR --host 127.0.0.1 --port 11439 \
  -c 2048 -np 1 --cache-ram 0 --ctx-checkpoints 0 -b 2048 -ub 512 \
  --fit off --no-ui --offline --swa-full -ngl all --device CUDA0

PYTHONPATH=convert python -m ollaya_convert.families.winnow.vision_parity \
  export http://127.0.0.1:11439 decision.json vision-goldens-cuda.json
```

For CPU use `-ngl 0 --device none --no-mmproj-offload` and save a separate CPU fixture.
After stopping the reference, start the runner (its first output line reports the port):

```sh
cargo build -p ollaya --locked
target/debug/ollaya runner --gguf MODEL --decision decision.json \
  --mmproj PROJECTOR --llama-dir LIBRARY_DIR --device cuda:0

PYTHONPATH=convert python -m ollaya_convert.families.winnow.vision_parity \
  check http://127.0.0.1:RUNNER_PORT vision-goldens-cuda.json
```

Use `--device cpu` with the CPU fixture. On Linux the CUDA dependencies must be on
`LD_LIBRARY_PATH`, and the CUDA backend must be installed where the runner discovers it.
The generated fixture records the stock build, server settings, request images and reference
log-probabilities. The export rejects a different build or mismatched context.

## Native HTTP and packaging

Use an isolated daemon/store with the vision tag and a text-only tag containing the same language
weights, decision and calibration layers; the latter can be a local alias of `winnow:e4b`.
The check unloads both models and expects an otherwise empty daemon:

```sh
PYTHONPATH=convert python -m ollaya_convert.families.winnow.vision_http \
  http://127.0.0.1:11438 winnow:e4b-vision winnow:e4b-text
```

The checked-in vision manifest is generated by `package_gguf` and `write_manifest`, not assembled
by hand. With the normal E4B export under `convert/out/winnow-e4b-q8_0`, this packages just that tag:

```sh
PYTHONPATH=convert python - <<'PYTHON'
from ollaya_convert.catalog import CATALOG
from ollaya_convert.package import Blobs, package_gguf, write_manifest
spec = CATALOG['winnow']
tag = 'e4b-vision'
config, layers = package_gguf(spec, tag, spec['tags'][tag], Blobs('https://ollaya.dev'))
write_manifest(spec['namespace'], spec['model'], tag, config, layers)
PYTHON

python -m unittest discover -s convert/tests -v
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
(cd site && OLLAYA_ALLOW_MISSING_BLOBS=1 npm run build)
```

The GGUF-only packaging path needs no ONNX/PyTorch installation. It still checks the export's
language-model source pin, obtains projector hash/size from the pinned author revision, and
writes derived metadata through the existing blob pipeline. Generated blobs and goldens stay
outside Git; maintainers publish the derived config blob with the registry tag.

## Scope

PNG still images only; no fetching URLs, audio or video. Existing text tags and text inference
remain unchanged. Text calibration is retained, with no measured visual calibration or benchmark
accuracy claim. Metal, Windows and Winnow-12B vision need separate runtime validation. The author's optimized
image server has not been compared: this branch uses the primary GGUF reference from ADR 0003,
stock pinned llama-server with Winnow's rendered image prompt and a fixed shared-prefix plan.
It makes no claim of image parity against the author's separate prefix/suffix tokenization plan.
